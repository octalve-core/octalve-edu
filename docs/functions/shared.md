# Shared — Functions (libraries used across the app)

What every other part leans on: the authentication library and the `withAuth` route guard (`src/lib/auth/`), the tenant machinery that keeps one school's rows from another's
(`src/lib/tenant/`), the API helpers (response envelope, validation, pagination), email, the Content-Security-Policy, the dispatch queue, the database client and the request proxy.

## `src/lib/auth/`

Who a person is and what they may do: sessions, the API and page guards, passwords, recovery and email-change links, rate limits, audit of person-level events and two-step verification (`mfa/`).

| File | Description |
| --- | --- |
| `administer.ts` | `canAdminister(holder, campusId)` and `isAdministrator(role)`. `canAdminister`: an `ADMIN` always, a `CAMPUS_ADMIN` only for a row of their own campus (a school-wide row, `campusId` null, is refused), every other role never. `isAdministrator` is true for `ADMIN` and `CAMPUS_ADMIN` and gates the edit controls of the people pages. Only `isAdministrator` has a caller in `src/`; `canAdminister` is called by tests only. |
| `audit.ts` | `auditPersonEvent(userId, action, details)`: records a person-level security event (`LOGIN_SUCCEEDED`, `PASSWORD_CHANGED`, `MFA_ENABLED`, `PROFILE_UPDATED`, `SESSION_REVOKED` and others) as an `AuditLog` row with `targetType` `User`, one per school the person actively belongs to, each written inside that school's tenant context. A person with no active membership (a platform administrator who belongs to no school) gets no row. Routes call it inside `after()`, so a failure never fails the request. |
| `authorize.ts` | `isAuthorized(holder, { roles, permissions })`: the one pure decision behind `withAuth`. Neither list: any active member. `roles` only: the member's role must be listed (an `ADMIN` is NOT implied). `permissions` given: the role is in `roles` (if given), OR the member is an `ADMIN` (admin implies every permission, never a role), OR holds one listed permission (ADR 0006). |
| `campus-scope.ts` | Route-level answers to "may this member change this row?" for a `CAMPUS_ADMIN` (ADR 0016): `judgeCampus`, `createCampus`, `ownCampusOnly`, `announcementAudience`, one lookup per kind of row (`studentScope`, `staffScope`, `guardianScope`, `sessionScope`, `periodScope`, `classGroupScope`, `armScope`, `armsScope`, `announcementScope`, `timetableSlotScope`, `invoiceScope`) and the read variants `studentReadScope`, `armReadScope`. Each returns `null` (go on) or a `Response`: another campus's row or an absent one is 404 `NOT_FOUND`, a school-wide row is 403 `FORBIDDEN` (404 for an invoice of a student with no campus); an `ADMIN` passes with no lookup. `tests/unit/route-role-guard.spec.ts` fails a campus-capable route that calls none. |
| `complete-sign-in.ts` | `completeSignIn(req, user, remember, extra)`: the one place a person becomes signed in, called by `/auth/login` (no second factor) and `/auth/login/mfa`. Deletes the session the browser presented, creates a new one (anyone holding an administrator role, a platform administrator included, gets the shorter absolute lifetime: 7 days instead of 90 when kept signed in), sets the cookie (persistent only when `remember`), and after the response audits `LOGIN_SUCCEEDED` with a device label, never an IP. Replies `{ user, ...extra }`. |
| `csrf.ts` | `validateCSRF(req)`: the same-origin check for state-changing requests (there are no CSRF tokens). Refuses a `Sec-Fetch-Site` of `cross-site` or `same-site`; then `Origin` (or `Referer`) must equal the request's `Host`, and a request with neither is refused. `X-Forwarded-Host` is read only when `TRUST_FORWARDED_HOST=true`. `withAuth` calls it for every method except GET, HEAD and OPTIONS; a route without `withAuth` must call it itself. |
| `email-change.ts` | `createEmailChangeToken(userId, newEmail)`, `confirmEmailChange(token)`, `EMAIL_CHANGE_LINK_MINUTES` (60): the two halves of changing an account's address. Only a SHA-256 hash of the 256-bit token is stored (`EmailChangeToken`), and a person keeps one request (creating one deletes the others). Confirming is one transaction with a conditional claim: it sets `User.email` and `emailVerified` and deletes all the person's sessions, reset links, sign-in challenges and other requests. It returns null for unknown, used, expired and "address taken" alike. |
| `mask-email.ts` | `maskEmail(email)`: `amina@school.example` becomes `a***@school.example`; anything not shaped like an address becomes `***`. Used in security notices (`lib/email/messages.ts`) and the invitation preview, so a full address is not spread around. |
| `memberships.ts` | `getUserMemberships(userId)` and the `UserMembership` type: the schools a person belongs to (tenant id, code, name, campus id, role), oldest first, read through the user context (`forUser`) before any tenant is known. Deactivated memberships and suspended schools are left out. Feeds `/auth/me` and the shell's navigation; only the campus id is returned, because campus names are tenant-scoped data. |
| `mfa/base32.ts` | `base32Encode` (RFC 4648 without padding, what `otpauth://` URLs use) and `base32Decode` (tolerates lower case, spaces, hyphens and `=`; any other character gives `null`, never a partial result). Only tests call `base32Decode`. |
| `mfa/challenge.ts` | The "pending second factor" between a correct password and a correct code (`MfaChallenge`): not a session, no cookie, invisible to `withAuth`. `createChallenge` (256-bit token, only its SHA-256 stored; 5-minute life; at most 5 live per person; carries the "remember" choice), `spendChallengeAttempt` (atomic conditional increment, 5 attempts, spent BEFORE the code is checked), `consumeChallenge` (exactly one caller wins), `deleteUserChallenges` (called when the password changes). |
| `mfa/codes.ts` | The browser-safe half of two-step verification (no `node:crypto`): `normaliseTotpCode` (6 digits, spaces and hyphens ignored, else null), `normaliseRecoveryCode` (10 characters of the Crockford alphabet; case and separators ignored, O read as 0, I and L as 1), `RECOVERY_CODE_ALPHABET`, `RECOVERY_CODE_LENGTH` and `RECOVERY_CODE_COUNT` (both 10). Forms and server share the rules, so a typo is caught before a request. |
| `mfa/factor.ts` | `parseSecondFactor(body)`: turns a request body into a `SecondFactor` (`{ code }` or `{ recoveryCode }`) only when EXACTLY one is present and shaped right; otherwise null. Routes answer null with 400 and refund their rate-limit slot, so a typo never counts as a guess. |
| `mfa/recovery-codes.ts` | `generateRecoveryCode` (`XXXXX-XXXXX`, 50 random bits from `crypto.randomInt`), `generateRecoveryCodes` (ten distinct) and `hashRecoveryCode` (HMAC-SHA256 under a key derived from `MFA_ENCRYPTION_KEY`, hex, stored in `MfaRecoveryCode.codeHash`; throws `MfaUnavailableError` without a key). Keyed because a 50-bit code could be ground offline from a table of plain hashes. Re-exports `RECOVERY_CODE_COUNT` and `normaliseRecoveryCode`. |
| `mfa/secret-box.ts` | Keys and encryption for two-step verification, failing closed: `MFA_KEY_ENV` (`MFA_ENCRYPTION_KEY`, base64 of 32 bytes), `mfaConfigured()`, `deriveKey(purpose)` (HKDF-SHA256), `encryptSecret` and `decryptSecret` (AES-256-GCM, `v1.<iv>.<ciphertext>.<tag>`, the user id bound as authenticated data so a row copied to another user does not decrypt) and `MfaUnavailableError`, which routes map to 503. No development fallback key exists. |
| `mfa/service.ts` | The data side of two-step verification for one person: `hasActiveMfa`, `getMfaStatus`, `unusedRecoveryCodeCount`, `beginEnrolment` (a new UNCONFIRMED secret, replacing an earlier unconfirmed one; null if a confirmed credential exists), `confirmEnrolment` (activates it, issues ten recovery codes), `verifyTotpForUser` (refuses a step at or below `lastUsedStep`, so a code cannot be replayed), `spendRecoveryCode`, `verifySecondFactor`, `regenerateRecoveryCodes`, `disableMfa`. Every use-once rule is a conditional UPDATE whose row count decides; routes own the HTTP and rate limits. |
| `mfa/totp.ts` | RFC 6238 TOTP over RFC 4226 HOTP, written in-house (HMAC-SHA1, 6 digits, 30-second steps, one step of drift either side) and checked against the RFC vectors in `tests/unit/totp.spec.ts`: `generateTotpSecret` (160 bits), `hotp`, `totpAt`, `stepAt`, `verifyTotp` (constant-time; returns the matched step and refuses a step at or below `afterStep`) and `otpauthUrl` for the QR code. Re-exports `normaliseTotpCode`. |
| `page-session.ts` | `requirePageSession()`: the session guard for pages (the API's is `withAuth`). No session redirects to `/login` with no return address; otherwise it returns `{ session, memberships, isPlatformAdmin }`. Wrapped in React `cache`, so the layout and the page share one database hit. Every page must call it (or `requireTenantPage`) itself: the layout only displays who is signed in. `isPlatformAdmin` is display data for the shell's Platform link. |
| `password-policy.ts` | Client-safe password rules with no Node imports: `PASSWORD_MAX_LENGTH` (128), `PASSWORD_MAX_BYTES` (72, all bcrypt reads), `passwordByteLength` and `checkNewPassword`, the one rule for a NEW password (setup, reset, change, invitation): at least 8 characters, at most 128 characters and 72 bytes, at least one Latin letter (`a-z`, `A-Z`) and one digit. Login does not use it, so older passwords keep working. |
| `password-reset.ts` | `createResetToken`, `isLiveResetToken`, `resetPasswordWithToken`, `RESET_TOKEN_TTL_MS`: single-use reset links in `PasswordResetToken` (SHA-256 hash only, 30 minutes, one live link per person). `resetPasswordWithToken` claims the token with a conditional update, sets the password hash and deletes every session, pending sign-in challenge and other link of that person in one transaction; the second factor is untouched. Null for unknown, used or expired. |
| `password.ts` | `hashPassword` (bcrypt cost 12 via `bcryptjs`; rejects a password over 72 bytes instead of letting bcrypt truncate it) and `verifyPassword` (always runs a compare, against a boot-time dummy hash when there is no user or no `passwordHash`, so "no such account" costs the same as "wrong password"). Re-exports `PASSWORD_MAX_LENGTH` and `PASSWORD_MAX_BYTES`. Server only. |
| `profile-policy.ts` | `checkName(input)` and `NAME_MAX_LENGTH` (100): the rule for a person's display name, client-safe (the profile form, `PATCH /account/profile` and invitation acceptance call it). Normalises (NFC, inner whitespace collapsed, trimmed) and refuses an empty name, more than 100 characters, and control or bidirectional-override characters. Zero-width joiners are allowed on purpose between letters, but a name with nothing visible in it (only zero-width characters, the byte-order mark, variation selectors, a soft hyphen or a filler) is refused like an empty one ("Enter your name."). The refusal pattern (line 9) writes the bidirectional characters as escapes, so they can be seen; tests/unit/source-hygiene.spec.ts keeps literal ones out of the source. |
| `pwned-password.ts` | Breached-password check against the Have I Been Pwned range API with k-anonymity: only the first 5 hex characters of the password's SHA-1 leave the server (`Add-Padding: true`). `isBreachedPassword` FAILS OPEN on any error or after 2 seconds; `PWNED_PASSWORD_CHECK=off` disables it and `PWNED_PASSWORD_URL` changes the endpoint. `checkNewPasswordOnServer` is `checkNewPassword` then the breach check and returns the sentence to show or null. Used by setup, reset, change and invitation acceptance. |
| `rate-limit.ts` | Reserve-then-refund sliding-window limiter: `reserveAttempt(key, limit = 5)`, `refundAttempt`, `checkRateLimit` (read-only) and `getClientIp`. One window for everything: `WINDOW_MS` is 5 minutes. The store is in-process memory by default (capped at 10,000 keys; limits multiply by instance count) or Redis (`RATE_LIMIT_STORE=redis` plus `REDIS_URL`), falling back to memory while Redis is down. `getClientIp` trusts only `CLIENT_IP_HEADER` (default `x-real-ip`, or the Nth entry from the right of `x-forwarded-for` per `TRUSTED_PROXY_HOPS`); with no header all clients share one `unproxied` bucket. |
| `reauth.ts` | `proveOwnPassword(userId, password)` and `passwordProofFailure(proof)`: re-asks a signed-in person for their own password before a consequential action. Constant-time check; 5 failures per account per window (`reauth:user:<id>`), a success is refunded; returns `ok`, `wrong` or `limited`. `passwordProofFailure` builds the 429 `RATE_LIMITED` or 403 `WRONG_PASSWORD` reply with a field error on `body.password`. Used by the platform guard, school settings and the academic-session activate and close routes. |
| `reset-constants.ts` | `RESET_LINK_MINUTES` (30): how long a password-reset link lives. No Node imports, so the reset email, the forgot-password form and the server read the same number. |
| `session-devices.ts` | The "active devices" list: `listSessions` (the person's unexpired sessions, the current one first and then the most recently used; each `SessionSummary` has the row id, a device label from the stored user agent, `createdAt`, `lastUsedAt`, `keptSignedIn`), `revokeOwnSession` (null when the session is unknown or someone else's, so ids cannot be probed) and `revokeAllOtherSessions`. Never exposes a token; `Session` has no IP column. |
| `session.ts` | Hand-rolled database sessions (`Session` table). `createSession` makes a 256-bit token and stores only its SHA-256. Idle window 30 days (slides, written at most every 5 minutes); absolute cap 90 days when "kept signed in" (7 days for anyone holding an administrator role) and 12 hours when not; at most 10 sessions per person (oldest evicted). `getSession` and `getSessionFromRequest` read the cookie (`__Host-octalve.session-token` when `APP_URL` is https, else `octalve.session-token`); `setSessionCookie` and `clearSessionCookie` use identical attributes. `ResolvedSession` carries `support` while a support view is open. `revokeUserSessions` and `purgeExpiredSessions` have no caller outside tests. |
| `user-agent.ts` | `describeUserAgent(ua)`: turns a stored user-agent string into a short label such as `Chrome on Windows` (browser and system matched in a fixed order, because Edge and Opera also say Chrome), or `Unknown device`. Used by the active-devices list and the sign-in audit row; only ever rendered as text. |
| `with-auth.ts` | `withAuth(handler, options?)`: the guard every API handler uses. In order: CSRF for every method except GET, HEAD and OPTIONS (403 `CSRF`); a session (401 `UNAUTHENTICATED`); with `{ tenant: true }`, `resolveTenant` (403, or 500 on a misconfigured install) and `isAuthorized` for `roles` and `permissions`, one 403 body for every refusal; the support-view rules; then the handler, which gets `auth.tenant.run(fn)`. `roles` or `permissions` without `tenant: true`, an empty or unknown `permissions` list or a non-array `roles` throw when the route is defined. `area` (ADR 0017): in a support view only a read to a route declaring a granted `area` gets through, and it is logged. Responses default to `private, no-store`. |

## `src/lib/tenant/`

The tenant trust boundary: how a request or a page becomes "this verified school", and the only doors to tenant-scoped data.

| File | Description |
| --- | --- |
| `assert-rls.ts` | `assertRlsEnforced()`, `checkRlsEnforcement()`, `rlsVerdict()`: asks Postgres who the app is connected as and refuses to serve tenant data when row-level security would be inert (the role is a superuser, has BYPASSRLS or owns the tables, or a table with a `tenantId` column lacks enabled and forced RLS). Runs once per process, before the first tenant resolution; a refusal is not remembered, so a fixed setup is picked up without a restart. In production a problem throws (every tenant route answers 500) unless `ALLOW_RLS_BYPASS=true`; elsewhere it warns once. |
| `for-tenant.ts` | The doors to tenant-scoped data. `forTenant(id).transaction(fn)` runs `fn` in one transaction (5 s to get a connection, 15 s in all) after `set_config('app.tenant_id', ..., true)` with a bind parameter and transaction-local scope; `id` must be a `VerifiedTenantId`. Siblings: `forUser` (a person's own memberships before any tenant is known; read-only by policy), `forInvitation` (the one `Invitation` row whose token hash matches), `forVerification` (public lookup by 32-hex token) and `setTenantContext` for code that creates a tenant and its first rows in one transaction (setup). |
| `page-tenant.ts` | `requireTenantPage(code, area?)`: the page-side twin of `withAuth(..., { tenant: true })`. Not signed in goes to `/login` (via `requirePageSession`); no such school or not a member calls `forbidden()` (the 403 view), one answer for both; a misconfigured install throws. Returns the session and the verified tenant with a `run`. It takes no roles: a role-limited page checks `tenant.role` itself. In a platform administrator's support view a page with no `area`, or outside the grant, is the 403 view, and each view is logged as `GET /schools/<code>` with its area (not the page path). |
| `resolve-tenant.ts` | `resolveTenant({ userId, code, support })`: the only place a request becomes a `VerifiedTenantId`. The URL code (trimmed, lower-cased, `isValidTenantCode`) is a lookup key only; the caller's own active `TenantMembership` in a non-suspended school decides. Returns the `TenantContext` (id, code, name, `schoolType`, role, `campusId`, `permissions`, optional `support`), 403 `FORBIDDEN` (one answer for no such school, bad code, not a member, deactivated, suspended) or 500 `TENANT_MISCONFIGURED` (RLS not enforced, or `DEPLOYMENT_MODE=solo` without exactly one tenant). A live support view with no membership yields a virtual ADMIN context. |
| `validate-code.ts` | `isValidTenantCode(code)` and `slugifyTenantCode(name)`: a tenant code is 2 to 40 characters of `a-z`, `0-9` and hyphen, minus 12 reserved words (`dashboard`, `admin`, `api`, `settings`, `list`, `login`, `logout`, `setup`, `schools`, `app`, `www`, `octalve`). The slug lower-cases, turns runs of other characters into one hyphen, trims hyphens and cuts at 40; the validator itself does not reject leading, trailing or doubled hyphens. Used by the resolver, the nav, the platform's school form, support and setup. |
| `verified-tenant.ts` | `VerifiedTenantId` (a branded string) and `trustedTenantId(id)`, the only way to make one. It refuses an empty or over-128-character id and proves nothing else, so call it only where the proof is in the lines above. ESLint forbids importing it in `src/app/(app)/schools/**` and `src/app/api/v1/schools/**` only; many `src/lib` services call it on the `tenantId` a route hands them. |

## `src/lib/api/`

Shared API plumbing: the response envelope, query-string pagination and request validation. Routes use them inside `withAuth`.

| File | Description |
| --- | --- |
| `envelope.ts` | `ok(data, meta, status)` and `fail(message, status, code, details)` build the PRD section 7 response shape `{ data, meta, error }` (the error code defaults to the status); `noStore(response)` adds `Cache-Control: no-store`; `ErrorDetail` is one field-level problem (`path`, `message`). |
| `pagination.ts` | Strict query-string pagination: `parseOffsetPagination` (`page` and `limit`, defaults 1 and 25, `limit` at most 100, `page` at most 100,000, giving `skip` and `take`), `offsetMeta`, and keyset cursors (`encodeCursor`, `decodeCursor`, `parseCursorPagination` with `limit` and `after`, `cursorMeta`). A repeated, empty, signed, decimal or out-of-range value is a 400 naming the field, never clamped. A cursor is base64url of `{ t, id }`, at most 256 characters, validated like any input. |
| `validate.ts` | `validate(schemas, handler)` and `parseRequest`, composed inside `withAuth`: check the query and body with zod and answer 400 `VALIDATION` (up to 20 `details`, paths prefixed `body.` or `query.`), 400 `INVALID_BODY` for non-JSON, 413 `PAYLOAD_TOO_LARGE` over `MAX_BODY_BYTES` (1 MiB; `maxBodyBytes` raises it for one route, never lowers it). A plain zod object strips unknown keys; a strict one refuses them. A body schema with an empty body is a 400. |

## `src/lib/queue/`

BullMQ queues and worker code for notification delivery (Redis); the communication service and event triggers enqueue through it.

| File | Description |
| --- | --- |
| `definitions.ts` | BullMQ queues: `QUEUE_NAMES` (`notification-dispatch-queue`, `bulk-broadcast-queue`), job data types, lazy singletons `getNotificationDispatchQueue` (3 attempts, exponential backoff from 1 s, keeps 1,000 completed and 5,000 failed jobs) and `getBulkBroadcastQueue` (2 attempts, backoff from 2 s), and `closeQueues`. Nothing imports `getBulkBroadcastQueue` or `BulkBroadcastJobData`. |
| `dispatch-service.ts` | `enqueueNotificationDispatch(params)`: in `forTenant` inserts a `NotificationDispatch` row with status `QUEUED`, then adds a BullMQ job `dispatch:<channel>:<id>` (priority 1 for SMS, else 5). Row and job are two steps with no compensation if Redis fails. `enqueueBulkNotificationDispatches(list)` calls it one recipient at a time in a loop. Used by `lib/communication/service.ts` and `event-triggers.ts`; no campus logic here. |
| `dispatch-worker.ts` | `processDispatchLifecycle(job, handler, attemptsMade, maxAttempts)`: under tenant RLS sets the `NotificationDispatch` row `PROCESSING`, runs the channel handler, then `SENT` plus an audit row `DISPATCH_SENT`, or `RETRYING` (`DISPATCH_RETRYING`) or, on the last attempt, `FAILED` (`DISPATCH_FAILED`), rethrowing a sanitized error so BullMQ retries. `sanitizeErrorMessage` redacts keys, tokens, passwords and Bearer values and cuts to 500 characters. `createNotificationDispatchWorker` builds the `Worker` (concurrency 5), but nothing in the repository calls it, so nothing consumes the queue. |
| `redis.ts` | Redis settings for BullMQ: `getQueueRedisOptions(customUrl?)` turns `REDIS_URL` (default `redis://127.0.0.1:6379`) into host, port, username, password and db with `maxRetriesPerRequest: null` and `lazyConnect`; no TLS option is set, whatever the URL scheme. Also `getQueueRedisClient` (a shared ioredis client, unused) and `closeQueueRedisClient` (test teardown). |

| `dev-tools.ts` | `appEnv()`, `devToolsAccess()` and `devToolsEnabled()`: the one decision on whether any development affordance exists; it fails closed. `appEnv`: `VERCEL_ENV=production` wins, then `APP_ENV` (an unrecognised value means production), else `NODE_ENV=production`. `devToolsAccess`: production `off`; staging `token` only with `DEV_TOOLS=true` and a non-empty `DEV_TOOLS_TOKEN`, else `off`; development `open` unless `DEV_TOOLS=false`. Used by the root layout, the `inbox` email transport and the dev inbox route. |
| `relative-time.ts` | `relativeTime(iso, now, locale)`: "3 days ago" style text from `Intl.RelativeTimeFormat` (units year down to minute; under a minute it says "just now"; an unparseable date gives an empty string). Pure, the clock is a parameter; used by `SessionsPanel`. |
| `roles.ts` | `ROLE_LABELS`: display names for the six `Role` values (`ADMIN` is "Administrator", `CAMPUS_ADMIN` "Campus administrator", then teaching staff, non-teaching staff, student, parent). The enum values are identifiers and must not be shown to people. |
| `theme.ts` | `THEME_COOKIE` (`theme`), type `Theme` (`dark` or `light`), `parseTheme` (anything but `light` is `dark`) and `THEME_MAX_AGE_SECONDS` (one year). The theme is a plain cookie so the server renders the right one on the first paint, with no inline script. |
