# Sign-in, account and set-up — Functions (libraries, API routes)

The API routes with no school in the URL: sign-in and sign-out, password reset, two-step verification, sessions, email change, the account profile, invitations, the first-run set-up
and public verification, with the invitation and set-up libraries. The authentication library they use is `src/lib/auth/` ([`shared.md`](./shared.md)).

## API routes: Auth (`/api/v1/auth/`)

Sign-in, sign-out, password recovery, email change, two-step verification and device sessions. None of these is a school route, so none declares a support `area` (ADR 0017: a support view limits school routes only). Every limit below is per 5-minute window (`WINDOW_MS` in `lib/auth/rate-limit.ts`), and "refunded" means the slot is handed back on success. A route without `withAuth` checks CSRF in its own handler; `withAuth` does it for every method except GET, HEAD and OPTIONS. Every response is uncacheable (`noStore`, or `withAuth` adds `private, no-store`).

| Method | Route | File | Who | Description |
| --- | --- | --- | --- | --- |
| POST | `/api/v1/auth/change-password` | `auth/change-password/route.ts` | Signed in (`withAuth`, no tenant); re-authenticates with the current password; no support `area` | Body `{ currentPassword, newPassword }`. Checks the current password in constant time (400 `INVALID_CURRENT_PASSWORD`), then the new one with `checkNewPasswordOnServer` (rules plus breach check, 400 `VALIDATION`; the same password is 400 `SAME_PASSWORD`). 5 attempts per account (429 `RATE_LIMITED`); success, a weak new password and a repeated one hand the slot back. Success stores the new hash, ends every OTHER session (this one stays), deletes pending sign-in challenges, and after the response audits `PASSWORD_CHANGED` and mails a notice. |
| POST | `/api/v1/auth/email-change/confirm` | `auth/email-change/confirm/route.ts` | Anyone (public): the one-time token in the link mailed to the new address is the credential; CSRF checked in the handler | Body `{ token }` (20 to 200 characters). `confirmEmailChange` claims the token and switches `User.email` (and sets `emailVerified`) in one transaction, deleting every session, password-reset link, sign-in challenge and other email-change request of that person. Unknown, used, expired and "address taken meanwhile" all give the same 400 `INVALID_TOKEN`. 10 failures per IP (success refunded). Success clears the session cookie, signs nobody in, and after the response audits `EMAIL_CHANGED` and notifies the old address. |
| POST | `/api/v1/auth/email-change/request` | `auth/email-change/request/route.ts` | Signed in (`withAuth`, no tenant); re-authenticates with the current password; no support `area` | Body `{ newEmail, password }`. A wrong password is 400 `INVALID_PASSWORD` (5 per account; every other outcome refunds); the caller's own address is 400 `SAME_EMAIL`; then 3 verified requests per account and 3 per target address. The answer is always `{ requested: true }`, whether or not the address has an account. After the response it notifies the OLD address, audits `EMAIL_CHANGE_REQUESTED`, and mails the new address either a 60-minute link (one live request per person) or a "taken" notice. |
| POST | `/api/v1/auth/forgot-password` | `auth/forgot-password/route.ts` | Anyone (public); CSRF checked in the handler | Body `{ email }`. Always answers 200 `{ requested: true }`, even for a malformed or unknown address or when the per-address limit is hit; the user lookup, token insert (30-minute link, one live link per person) and mail all run after the response, so neither body nor timing says whether the account exists. Limits are never refunded: 10 per IP (429 `RATE_LIMITED`) and 3 per address. |
| POST | `/api/v1/auth/login/mfa` | `auth/login/mfa/route.ts` | Anyone (public): the challenge token from `POST /auth/login` plus a current second factor; CSRF checked in the handler | Sign-in step 2. Body `{ challenge, code }` or `{ challenge, recoveryCode }` (exactly one). 503 `MFA_UNAVAILABLE` without `MFA_ENCRYPTION_KEY`. Each try spends one of the challenge's 5 attempts BEFORE the code is checked (401 `INVALID_CHALLENGE` once it is dead or past 5 minutes), plus 10 failures per account and 30 per IP; a wrong code is 401 `INVALID_CODE`. Success consumes the challenge and creates the session via `completeSignIn` with the "keep me signed in" choice made at step 1; a spent recovery code also returns `recoveryCodesRemaining`, audits `MFA_RECOVERY_CODE_USED` and mails the person. |
| POST | `/api/v1/auth/login` | `auth/login/route.ts` | Anyone (public); CSRF checked in the handler | Sign-in step 1. Body `{ email, password, remember }` (`remember` is a strict boolean, default false). A body that fails validation, an unknown account and a wrong password are all 401 `INVALID_CREDENTIALS` (the last two after a constant-time bcrypt compare). Failures only count: 30 per IP, 5 per IP and email (429, plus one `LOGIN_BLOCKED` audit row per window for a real account), and a soft 10 per email that only sets `accountThrottled` in the reply. With active two-step verification it returns `{ mfaRequired, challenge }` and NO session; otherwise `completeSignIn` sets the cookie. |
| POST | `/api/v1/auth/logout` | `auth/logout/route.ts` | Anyone (public); CSRF checked in the handler; no support `area` | Deletes the `Session` row that matches the cookie's token hash and clears the cookie with the attributes it was set with. Idempotent: no cookie or an unknown one still answers 200 `{ loggedOut: true }`. No rate limit. |
| GET | `/api/v1/auth/me` | `auth/me/route.ts` | Signed in (`withAuth`, no tenant); no support `area` | Returns `{ user, memberships }`: the session's user (`id`, `name`, `email`) and the schools the person belongs to (`getUserMemberships`: tenant id, code, name, campus id, role; deactivated memberships and suspended schools are left out). |
| POST | `/api/v1/auth/mfa/confirm` | `auth/mfa/confirm/route.ts` | Signed in (`withAuth`, no tenant); proves possession with a current authenticator code; no support `area` | Step 2 of turning two-step verification on. Body `{ code }` (6 digits). 409 `NOT_ENROLLING` with no pending enrolment, 400 `INVALID_CODE`, 503 without `MFA_ENCRYPTION_KEY`; 5 wrong codes per account (success refunded). Success activates the credential, returns the ten recovery codes once, ends every other session, and after the response audits `MFA_ENABLED` and mails a notice. |
| POST | `/api/v1/auth/mfa/disable` | `auth/mfa/disable/route.ts` | Signed in (`withAuth`, no tenant); re-authenticates with the password AND a current second factor; no support `area` | Body `{ password, code }` or `{ password, recoveryCode }`. The password is checked first (400 `INVALID_PASSWORD`) so a wrong password never burns a one-time code, then the factor (400 `INVALID_CODE`); 409 `NOT_ENABLED` when it is off, 503 without a key; 5 failures per account (success refunded). Success deletes the credential, every recovery code and pending challenge, ends every other session, audits `MFA_DISABLED` and mails a notice. |
| POST | `/api/v1/auth/mfa/enroll` | `auth/mfa/enroll/route.ts` | Signed in (`withAuth`, no tenant); re-authenticates with the current password; no support `area` | Step 1 of turning two-step verification on. Body `{ password }` (400 `INVALID_PASSWORD`; 5 wrong per account, success refunded; 503 without `MFA_ENCRYPTION_KEY`). `beginEnrolment` stores a fresh secret encrypted and UNCONFIRMED (it protects nothing until `/mfa/confirm`) and returns `{ secret, otpauthUrl }` once; the page draws the QR code in the browser. 409 `ALREADY_ENABLED` if a confirmed credential exists. Writes no audit row. |
| POST | `/api/v1/auth/mfa/recovery-codes` | `auth/mfa/recovery-codes/route.ts` | Signed in (`withAuth`, no tenant); proves possession with a current authenticator code (a recovery code is not accepted); no support `area` | Body `{ code }`. Replaces ALL recovery codes, used or not, with ten new ones returned once. 409 `NOT_ENABLED`, 400 `INVALID_CODE`, 503 without a key; 5 wrong per account (success refunded). After the response it audits `MFA_RECOVERY_CODES_REPLACED` and mails a notice. Unlike enable and disable it does not end other sessions. |
| POST | `/api/v1/auth/reset-password` | `auth/reset-password/route.ts` | Anyone (public): the one-time token in the emailed link is the credential; CSRF checked in the handler | Body `{ token, password }`. The new password is checked (rules plus breach check, 400 `VALIDATION`) BEFORE the link is spent; `resetPasswordWithToken` then claims it in one transaction, stores the hash and deletes every session of the person, their pending sign-in challenges and other reset links (the second factor stays). Dead links are one 400 `INVALID_TOKEN`; 10 failures per IP (success refunded). Signs nobody in, clears the cookie, audits `PASSWORD_RESET` and mails a notice after the response. |
| POST | `/api/v1/auth/sessions/revoke-others` | `auth/sessions/revoke-others/route.ts` | Signed in (`withAuth`, no tenant); no password needed (it can only reduce access); no support `area` | Signs the caller out of every other device: deletes all their `Session` rows except the current one and returns `{ revoked: count }`. 10 per account (429). Audits `SESSIONS_REVOKED` with the count after the response, only when the count is above zero. |
| POST | `/api/v1/auth/sessions/revoke` | `auth/sessions/revoke/route.ts` | Signed in (`withAuth`, no tenant); only the caller's own sessions; no support `area` | Body `{ sessionId }`. Ends one of the caller's OTHER sessions: the current one is refused (400 `CURRENT_SESSION`), and a session that is unknown or someone else's is the same 404 `NOT_FOUND`, so ids cannot be probed. 30 per account (429). Returns `{ revoked: true, device }` and audits `SESSION_REVOKED` with the device label after the response. |
| GET | `/api/v1/auth/sessions` | `auth/sessions/route.ts` | Signed in (`withAuth`, no tenant); only the caller's own sessions; no support `area` | Lists the caller's unexpired sessions as `{ sessions }` (`listSessions`): row id, device label parsed from the stored user agent, `current`, `createdAt`, `lastUsedAt`, `keptSignedIn`. The current one is first. Never a token, never an IP address. |

## API routes: Account (`/api/v1/account/`)

The signed-in person's own account. It is not a school route, so it declares no support `area` (ADR 0017: a support view limits school routes only).

| Method | Route | File | Who | Description |
| --- | --- | --- | --- | --- |
| PATCH | `/api/v1/account/profile` | `account/profile/route.ts` | Signed in (`withAuth`, no tenant); acts on the caller's own account only; no support `area` (not a school route) | Changes the caller's display name (`User.name`). Body `{ name }`; `checkName` normalises it (NFC, spaces collapsed) and refuses an empty name, more than 100 characters, and control or bidirectional-override characters (400 `VALIDATION`). Every attempt counts toward 10 per account per 5 minutes and is never refunded (429 `RATE_LIMITED`). Returns `{ user: { id, name, email } }`; when the name changed, a `PROFILE_UPDATED` audit row with before and after is written after the response, one per school the person belongs to. |

## `src/lib/invitations/`

Invitation links: the token, the derived status, the email and the service used by the administrator's and the invitee's routes.

| File | Description |
| --- | --- |
| `deliver.ts` | `mailInvitation({ to, token, schoolName, role, inviterName })`: sends the invitation email, meant to be called from `after()` so it never delays or fails the request. At most 5 mails per address per 5-minute window across all schools (`invite:mail:<address>`); beyond that the invitation exists and the mail is silently withheld. The resend route repeats this logic inline instead of calling it. |
| `service.ts` | Administrator side, in the tenant context: `createInvitation`, `resendInvitation`, `revokeInvitation`, `listOpenInvitations`. Invitee side, through `forInvitation(hash)`: `previewInvitation`, `acceptInvitation`. One open invitation per school and address (advisory lock; the earlier one is revoked and audited); a campus administrator invites only into their own campus and never at administrator level. Accepting is one transaction: a conditional update claims the link (single use), then the account is created or the signed-in owner attached, the membership created or reactivated, a named staff record linked, and `INVITATION_ACCEPTED` audited. Bad links give one answer; no audit row holds a token or hash. |
| `status.ts` | `invitationStatus` and `isLiveInvitation`: accepted, revoked, expired or pending, derived from `acceptedAt`, `revokedAt` and `expiresAt` and never stored. Pure and client-safe; the API, the Users page and the accept route share it. |
| `token.ts` | `newInvitationToken` (32 random bytes as base64url, always 43 characters), `hashInvitationToken` (SHA-256 hex, the only form stored), `isInvitationToken` (shape check `^[A-Za-z0-9_-]{43}$`), `INVITATION_TTL_DAYS` (7) and `INVITATION_TTL_MS`. The link carries the token in the URL fragment. |

## API routes: Invitations (`/api/v1/invitations/`)

The invitee's two calls, made before anyone has a membership; neither uses `withAuth` (the token in the body is the credential, CSRF is checked by hand, each call is limited per IP).

| Method | Route | File | Who | Description |
| --- | --- | --- | --- | --- |
| POST | `/api/v1/invitations/accept` | `invitations/accept/route.ts` | Anyone (public); the invitation token is the credential | Body `{ token, name?, password? }`. Accepts in one transaction. No account for the address: creates one from `name` and `password` (checked before the link is spent, 400 `VALIDATION`; breached passwords refused) without signing the person in. Signed in as the invited account: creates the membership. Account exists and nobody signed in: 409 `SIGN_IN_REQUIRED`; signed in as someone else: 403 `WRONG_ACCOUNT`; already a member: 409 `ALREADY_MEMBER`. Bad, used, revoked or expired links: one 400 `INVALID_TOKEN`. 10 failures per IP per 5 minutes (429; successes and sign-in prompts are refunded). |
| POST | `/api/v1/invitations/preview` | `invitations/preview/route.ts` | Anyone (public); the invitation token is the credential | Body `{ token }`. What the accept page shows before anyone commits: `schoolName`, `role` and `roleLabel`, a masked address, whether that address already has an account anywhere on the platform (`accountExists`) and whether the caller is signed in as it (`viewer`: none, invitee or other). Writes nothing. Invalid, used, revoked and expired links are one 400 `INVALID_TOKEN`. 40 requests per IP per 5 minutes, never refunded (429). |

## `src/lib/setup/`

Helpers for the Solo install's first-run wizard: which kind of school a new school is, and whether setup has been done.

| File | Description |
| --- | --- |
| `school-type.ts` | `SCHOOL_TYPES` (`K12`, `HIGHER_ED`, `VOCATIONAL`) and `defaultSchoolType()`: reads `DEFAULT_SCHOOL_TYPE` from the environment (unset or blank gives `K12`) and THROWS on any other value, so a typo stops setup instead of making the wrong kind of school. The kind of school never comes from the browser; `POST /api/v1/setup` calls this before it writes anything. |
| `status.ts` | `isSoloMode()` (`DEPLOYMENT_MODE` is `solo`) and `isSetupComplete()`, which reads the `SystemSettings` row `global`. It returns `null` (unknown) on a database error instead of throwing, and callers treat unknown as "do not redirect", so a database blip cannot lock a deployer out of setup. Used by the `/login` and `/setup` pages; the setup API route keeps its own copy of the Solo check. |

## API routes: Setup (`/api/v1/setup/`)

The Solo install's first-run bootstrap. It has no `withAuth` (no session exists yet) and is not a school route, so it declares no support `area`.

| Method | Route | File | Who | Description |
| --- | --- | --- | --- | --- |
| GET, POST | `/api/v1/setup` | `setup/route.ts` | Anyone (public), and only while `DEPLOYMENT_MODE=solo`: both methods answer 404 `NOT_FOUND` in any other mode. POST also needs `SETUP_TOKEN` when the server sets one; CSRF checked in the handler | GET returns `{ setupComplete, requiresToken }` (failing open to `setupComplete: false` on a database error). POST is the one-time bootstrap: one transaction creates the `Tenant`, the first `User` and an ADMIN `TenantMembership` and writes a `SETUP_WIZARD_COMPLETE` `AuditLog` row, after an atomic false-to-true flip of `SystemSettings.setupComplete` (a second caller gets 409 `ALREADY_COMPLETE`). Guards in order: CSRF, 5 attempts per IP (success refunded), refusal of a body that names `schoolType` (the type is `DEFAULT_SCHOOL_TYPE`), validation, breached-password check, then the setup token (`x-setup-token` header or body `setupToken`, timing-safe). Replies 201; signs nobody in. |

## API routes: Public verification (`/api/v1/verify/`)

Outside verifiers check a published result without signing in. It is not a school route, so it declares no support `area`.

| Method | Route | File | Who | Description |
| --- | --- | --- | --- | --- |
| GET | `/api/v1/verify/[token]` | `verify/[token]/route.ts` | Anyone (public): no `withAuth`; the 32-character hex verification token in the URL is the credential | `verifyPublicCredential` finds the `Result` whose `verificationToken` matches and whose status is `PUBLISHED` or `LOCKED`, reading through the `forVerification` database context, and returns `{ verified, institution, studentName (in full), academicSession, academicPeriod, subject, gradeLetter, publishedAt, verificationHash }` (no admission number). A token that is not 32 lowercase hex characters is 400 `INVALID_TOKEN`, an unknown one 404 `NOT_FOUND`; 60 attempts per IP per 5 minutes (429). Every response is `no-store` with `X-Robots-Tag: noindex, nofollow` (ISS-0008). |

## API routes: Certificate verification (`/api/v1/verify-certificate/`)

The public lookup of a vocational certificate by its verification token. It is not the route for published results, which is `/api/v1/verify/[token]`.

| Method | Route | File | Who | Description |
| --- | --- | --- | --- | --- |
| GET | `/api/v1/verify-certificate/[token]` | `verify-certificate/[token]/route.ts` | Anyone (public). No `withAuth`; the only protection is a per-IP limit of 60 requests per 5-minute window (`reserveAttempt` key `verify:cert:ip:<ip>`; the window is `WINDOW_MS` in `rate-limit.ts`). | Looks up an ISSUED certificate by its 32-character token (lower-case hex, the `verificationToken` the school gives the holder) and answers `verified` (hash recomputed), number, title, the student's name in full, school, issue date, period and the stored free-form `metadata`; no id, admission number or token. 429 `RATE_LIMITED`; 400 `INVALID_TOKEN` for anything that is not 32 lower-case hex characters (a certificate number included: it identifies a certificate and is not a credential); 404 `NOT_FOUND` for an unknown token, a DRAFT or a REVOKED certificate. The row is found through the `certificate_public_verification` policy (token and ISSUED), then the school's context is set to join the student, school and period. Every response is `no-store` with `X-Robots-Tag: noindex, nofollow`. |
