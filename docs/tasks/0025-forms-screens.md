## 1. Objective
Every route of the Forms module and the question bank's reports, printing and offer-back has a screen a person can reach by clicking, with the same rules as AlEemaan's (task 0041 there; the screens are the same product): a teacher sets and marks practice sets, questionnaires and paper work, a pupil takes them and practises, anyone with the link answers a public questionnaire, a reviewer handles reports on questions. Nothing about who may see what changes: the APIs decide (task 0024 and the parity note); the screens only show it.

## 2. Context & what was found
- **Correction (2026-11-02).** An earlier note said Octalve had no Forms module. That came from reading a checkout 28 commits behind. `origin/dev` (e39bd56) has the whole backend: `src/lib/forms/` (practice sets, questionnaires, paper work, marking), `src/lib/question-bank/` (items, reviewers, settings, practice, reports, regrade, printing, assessments), the routes under `/api/v1/schools/[code]/forms`, `.../portal/forms`, `.../portal/practice` and `.../question-bank`, and the migration `20261102120000_forms_and_question_bank_parity`. What it lacks is the screens: only Browse, My questions, Review queue, Reviewers and Settings exist.
- **Design source:** AlEemaan's `docs/tasks/0041-forms-screens.md` (the six rules every screen keeps) and its `src/components/forms/`, `src/components/portal/`, `src/components/question-bank/` (the ports start from those components, adapted to Octalve's API shapes below).
- **Differences that shape the port.** (1) Routes are `/api/v1/schools/[code]/...`; the campus is the caller's own (`auth.tenant.campusId`), so no screen sends a branch. (2) A pupil signs in with their own account (`STUDENT`), there is no portal session, and Octalve's navigation shows a pupil only Overview today: the pupil's screens need a page and a navigation entry. (3) The print routes answer with the PDF itself, not JSON (`format: json` does not exist). (4) The print log has no paging (a limit of at most 100). (5) A report's list has no `itemVersion`. (6) The offer-back route takes no `quizId` (the question id is enough). (7) The quiz list in the LMS panel carries counts only; a quiz's questions come from `GET .../lms/quizzes/[id]`.

**What ran, on one build:** all of `tests/unit`; the API specs `forms-gaps`, `forms-campus-scope`, `forms-public-questionnaire`, `forms-answer-key`, `forms-marking-rules`, `forms-results-grant`, `questionnaire-anonymity`, `portal-practice`, `portal-practice-set-guards`, `practice-summary-archive`, `question-report-guards` and `question-bank-printing`; the e2e specs `forms-screens`, `learn-screens`, `question-bank-reports`, `question-bank-print`, `shell`, `question-bank-questions` and `question-bank-admin-screens`. **Results:** the first group on one build: 1,046 passed, 4 failed, 19 skipped (the skips are the shell spec's phone-only tests on the desktop project and its desktop-only tests on the phone project, which skip by design). The four failures were one test bug in the new print spec (a quiz seeded with a staff foreign key), fixed. After the fixes, a fresh build (it carries the wording change below) and a focused run of `route-area-guard`, `shell-nav`, `forms-gaps`, `forms-screens`, `learn-screens`, `question-bank-print` and `question-bank-reports`, desktop and phone: 100 passed, 0 failed. The shell and the two older question-bank specs were in the first group and were not repeated on the last build, which changed five strings and one link.

**What the first runs found, and what was done** (none of it a change of who may see what):
- The practice-set builder sent `null` for a blank instructions field, window or time limit, and the create route accepted only a string or nothing, so a practice set with no window was refused with "expected string, received null". The route now accepts `null` for those four fields, as the questionnaire and paper-work routes already did; a spec covers it.
- The marking queue's link to a form's page lacked the school's code, so it led nowhere (and the browser's prefetch of it was a 404). It now carries the code, like the Forms list.
- Two new portal GET routes (`practice/sessions/[id]`, `practice/children`) did not declare a support area, which `route-area-guard` requires; both declare `academics`, as their neighbours do.
- Five strings in the Forms screens said "branch", AlEemaan's word; Octalve's is "campus" (or no word at all where the form is meant for everyone).
- The rest were mistakes in the specs, not in the code under test: a second person signing in inside the first person's browser session (each now has a context of their own), a guardian test that read the list of children before it had loaded, retiring a question needs a reason, a request that was meant to be refused was a valid one, a quiz seeded with a field that is a staff foreign key, and a marked attempt looked for in the "waiting" list (the queue follows: it moves to "Marked").

**Not run:** the whole suite (only the group above and its neighbours); a failing-first run of every new spec on an unfixed build of `dev` (the screens, the new routes and the new tab do not exist there, so the specs fail by construction; this was not run to confirm it, HANDOVER 7.2 item 2); mutation passes (deferred to the end of Phase 2, the maintainer's call).
