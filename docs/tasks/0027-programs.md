## 1. Objective
A program is learning that is not a normal class (a Quran memorisation program that never ends, a three-year course): it has its own levels (1 to 4 names the program chooses), a tree of groups, its own people and staff, and is run by the school's administrator plus a program admin they name. Octalve Edu gets the same, on its own foundations: a school (`Tenant`) with campuses, row-level security, composite foreign keys.

## 2. What is the same, and what is not (read from the code on 2026-11-04)
Same (see AlEemaan's 0043 for the reasoning): the program's kind (ongoing or fixed-term, the end date is start + duration - 1 day), the status flow (`DRAFT`, `ACTIVE`, `ARCHIVED`; `COMPLETED` only by the completion slice), up to four level names, the group tree with its rules (unique live names, no archiving a group with a live group inside), nothing hard-deleted (ADR 0004), an append-only audit, a 404 for a program the caller has no place in, hiding a button is a courtesy.

Different, on purpose:
1. **Tenant and RLS.** Every new table carries `tenantId`, has row-level security enabled and forced, and uses composite foreign keys (ADR 0001); the routes live under `/api/v1/schools/[code]/programs` and the pages under `/schools/[code]/programs` (the school's code is in the URL), and run inside `forTenant(tenantId)`. A source test (`tests/unit/route-role-guard.spec.ts`) fails a route that does not say who may call it, so every program route declares its roles.
2. **Campuses, not branches.** A school can have no campuses at all (`SchoolSettings.multiCampusEnabled` is false by default and `Campus` is optional on people). A program therefore either runs **school-wide** (no campus list: the only option for a school with no campuses) or in **chosen campuses** (`ProgramCampus`, one or more). A program can be created with a campus of its own (a real `Campus` row, only when `multiCampusEnabled` is on).
3. **Roles.** `ADMIN` is the school-wide administrator (AlEemaan's super admin); `CAMPUS_ADMIN` runs one campus (AlEemaan's branch admin; ADR 0016: a row of another campus is a 404, a school-wide row is not theirs). Only an `ADMIN` creates a program and names its program admins. A program admin must hold an **active** membership (not deactivated) with a staff role whose campus is empty or one of the program's campuses; the authority is read at every request, so deactivating the membership ends it at once.
4. **One membership per person per school** (`@@unique([userId, tenantId])`), with an optional campus. So "a person through a campus" is the **record's** campus (`StudentRecord.campusId`, `StaffRecord.campusId`, both nullable). A person whose record has no campus is "through the school": only an `ADMIN` or a program admin handles them, and a campus administrator never sees them.
5. **Guardians are real records here** (`GuardianRecord`, linked to students). So the participant kinds are `STUDENT`, `STAFF`, `GUARDIAN` (linked to a `GuardianRecord`), and the standalone `ADULT` and `CHILD`.
6. **The ceiling switch needs a settings store that Octalve does not have.** `SchoolSettings` is typed columns, one row per school; the only key and value store with a campus is `QuestionBankSetting`. The first slice adds one small generic table (tenant, optional campus, key, JSON value, updated by) with RLS, which the programs switch (`programs.enabled`: the school's value AND the campus's, a campus can only turn it off), the standing switch (task 0028) and the part-payment rule (task 0029) all use. A change of a school-wide value uses the existing step-up proof of the settings screen (it is the safer reading of PRD section 14); a campus narrowing does not.
7. **Where it sits in the sidebar.** `navFor(school, platform)` is role-based and carries a section per entry: Programs goes in **Learning**, for every staff role, kept in step with AlEemaan's Classroom section.

## 6. Build record, slice P1 (2026-11-09)
**What exists.** The migration `20261116090000_programs_structure` (additive: four enums, six tables: `Program`, `ProgramCampus`, `ProgramLevelLabel`, `ProgramGroup`, `ProgramStaff`, `ProgramAudit`; every one carries `tenantId`, composite foreign keys and forced row-level security; a live program's name is unique per school and a live group's name per parent, ignoring case; checks hold the levels (0 to 3), the top group having no parent, and a fixed-term program's dates; the audit is append-only by `REVOKE UPDATE, DELETE, TRUNCATE`). `src/lib/programs/` (rules, validation, access, common, settings-service, service, structure-service, staff-service, http), eleven routes under `/api/v1/schools/[code]/programs` and `settings/programs`, the pages `/schools/[code]/programs` and `.../[id]` (Overview, Structure, Admins, History), the Programs setting on the Settings page (the generic switch panel, shared with Discipline) and "Programs" in the sidebar's Learning section for every staff role.

**Decisions made while building.**
- Authority is read at every request. `ADMIN` is the school-wide administrator ("SUPER"); a program admin is a staff member the school's administrator names, who counts only while their membership is active and their campus is empty or one the program runs in (a school-wide program takes any campus); a `CAMPUS_ADMIN` reads the programs that run in their campus (a school-wide program is not theirs) and changes none. A program the person has no place in is a 404, the same as one that does not exist. A deactivated membership is refused at the door (403) like any non-member.
- A program runs school-wide (no campus rows) or in chosen campuses. It is **not** narrowed from school-wide to campuses afterwards (it would change who may see it), nor made school-wide by removing its last campus; a campus an admin serves through cannot be removed.
- Only the school's administrator makes a program, names or ends a program admin, restores an archived program, and adds or removes a campus. A program admin changes the details, the level names, the groups and activates or archives.
- The `programs.enabled` switch is the shared ceiling switch over `TenantSetting` (the school's value with the fresh proof; a campus can only turn it off). With programs off nothing can be made or changed and only the school's administrator reads; a campus that has them off cannot be given a program.
- Everything is audited in `ProgramAudit` (who, what, before and after); the history tab is shown to the people who manage the program; names come from the school's own memberships.
- Left out on purpose: a program with a campus of its own (the AlEemaan "own branch"): it needs the school's campus module and `multiCampusEnabled`, and no school asked for it; a program that wants a campus of its own is made in a school-wide way or with an existing campus.
- The groups' people (P2), the staff roles and the groups they are assigned to (P3), assessments, fees and certificates are not built; the structure service says where their refusals will go (archiving a group with people in it).

**Hosted databases.** The maintainer runs `20261116090000_programs_structure` (after `20261115090000_standing`); not run on any hosted database here.

## 7. Build record, slices P2 to P5 (2026-11-09)
**What exists.** Six additive migrations, to be run in this order after `20261116090000_programs_structure`: `20261117090000_standing_participant_subject` (one enum value, a migration of its own because PostgreSQL cannot use a value in the transaction that added it), `20261117100000_program_people`, `20261118090000_program_attendance`, `20261119090000_program_assessments`, `20261120090000_program_fees` and `20261121090000_program_completion`. Each is additive; the release before it never reads any of it, so each can be run before the code that uses it is deployed. Every table carries `tenantId`, composite foreign keys and forced row-level security; the histories (`ProgramAttendanceChange`, `ProgramScoreChange`) are append-only for the application's role (`REVOKE UPDATE, DELETE, TRUNCATE`).
- **P2 People.** `ProgramParticipant` (kinds `STUDENT`, `STAFF`, `GUARDIAN` linked to the school's records; `ADULT` and `CHILD` typed in), one place per person in one group through one campus (or through the school), the state of a place read from the school's own records and never copied (`placeState`), the standing of a person typed in (suspend, lift, expel, reinstate, with the history in `StandingEvent`), the namesake guard, adding a whole class (preview then confirm), the People tab, head counts on the Structure tab. A group with an open place, or a campus with people who are or were in it, cannot be archived or removed.
- **P3 Staff and attendance.** The roles supervisor, teacher and recorder, the groups a teacher or recorder is assigned to (covering the groups inside), sessions and the roll call (7-day window for teachers and recorders, any past day for an administrator, a supervisor corrects with a reason, a stale version is refused), the summary, the sessions of a week and a person's history. `programs.attendance.enabled` is a switch at three levels (school, campus, the program's own flag); a campus that has it off only leaves its own people out.
- **P3b Assessments.** Assessments (a dated sitting with a maximum, a pass mark, a weight, given to the whole program or to chosen groups), scores (a number or a code), grade bands, results over the published assessments, and the append-only score history. The program's own switch defaults off.
- **P4 Fees.** Tables of their own (the school's `Invoice` and `Payment` are not touched): fee items with an audience, exemptions, invoices (one per person and period, made by a preview-then-confirm step), manual payments under the school's part-payment rule, discounts, "pay in full only" on one invoice, a collection report. Numbers `PINV-YYYY-NNNN` and receipts `PRC-YYYY-NNNN` come from `ProgramCounter`.
- **P5 Completion and certificates.** Completing a place (any time) or a whole fixed-term program (after its end date, with a preview), a completion rule (an average and/or every required assessment passed) with an override and a reason, `noCertWhileOwing`, certificates (the wording, the name and the signatories as they were when issued; a 32-character code; withdrawn, never deleted), the print page `/schools/[code]/programs/[id]/certificates/[certId]`, and the public check at `/api/v1/verify-certificate/[token]` (first name and last initial only; the policy `program_certificate_public_verification`).
- **Settings.** The program's Settings tab (attendance, assessments with grade bands, fees, the certificate wording and the completion rule, progress records) and four more switch panels on the school's Settings page (attendance, assessments, fees, progress records and what pupils and guardians see of them).

**Decisions made while porting** (the safest option each time; any can be changed):
- A person's campus is the campus of their record when they are added and stays so; a person with no campus is "through the school" and only the school's administrator and a program admin handle them. A campus administrator never sees them.
- The ceiling switches share one mechanism (`ceilingSwitch` over `TenantSetting`) and one feature-state helper (`featureStateOf`) for attendance, assessments, fees and progress records.
- A guardian is a linked kind of participant (Octalve has real guardian records), so there is no "guardian name and phone typed in" for pupils: a pupil's billing contact is the primary approved guardian link.
- **Not built (honest limits):** paying a program invoice through the payment gateway (starting a payment and the webhook that completes it): staff record a payment taken outside; a screen for fee exemptions (they are set when an item is made or changed); the lock times of progress records are set through the API only (the Settings tab shows the other progress settings).

**Hosted databases.** The maintainer runs the six migrations above, in order; none was run on any hosted database here.
