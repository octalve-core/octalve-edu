## 1. Objective

An administrator who rolled a class by mistake (the wrong class, the wrong target session, the wrong decisions) can undo that roll as a whole: every pupil goes back to the place they had before, and the roll stays in the history as a roll that was undone, with who undid it and why. It is refused, with the reasons named pupil by pupil, when the new placements have already been used.

## 2. Context

- `executePromotion` (`src/lib/promotion/service.ts`) takes a class's ACTIVE enrolments in the source session and, for each pupil under a row lock, sets the source enrolment to PROMOTED, REPEATED, ALUMNI (graduated) or WITHDRAWN and, for a promotion or a repeat, creates a new ACTIVE enrolment in the target session. It writes a `PromotionBatch` and one `PromotionRecord` per pupil, once.
- Both promotion tables are APPEND-ONLY (`REVOKE UPDATE, DELETE, TRUNCATE ... FROM app_user`): a roll is evidence of what was decided and by whom. `PromotionRecord.targetEnrollmentId` is a composite foreign key to `StudentEnrollment` with `ON DELETE RESTRICT`, and an enrolment is unique per pupil and session (`@@unique([tenantId, studentId, sessionId])`). So an undo can neither edit the batch nor delete the enrolment it created, and a leftover enrolment row must not block rolling that pupil again.
- Everything that selects pupils by an ACTIVE enrolment drops a pupil whose enrolment is not ACTIVE without a change (the same reason `EXPELLED` exists, task 0028). `enrolWithin` (`src/lib/people/students.ts`) already revives a WITHDRAWN enrolment in the same session instead of duplicating it.

## 3. Decisions

- **D1. An undo is a new fact, never an edit.** A new append-only table `PromotionReversal` (one row per undone batch: `UNIQUE (tenantId, batchId)`, so a roll is undone at most once; the administrator, the reason, the counts, when). The batch and its records are untouched. Row-level security and the revoke of UPDATE, DELETE and TRUNCATE like every promotion table; composite foreign key to the batch. The history shows the roll as undone.
- **D2. A new enrolment status, `CANCELLED`.** The new placement of a promoted or repeating pupil cannot be deleted (D-context) and "withdrawn" would say the pupil left a class they never joined. `CANCELLED` means exactly "the roll that placed this pupil here was undone"; everything that selects by ACTIVE already ignores it. Migration `20261126090000_promotion_undo` (`ALTER TYPE "EnrollmentStatus" ADD VALUE 'CANCELLED'` and the table), additive, after `20261125090000_report_remarks`. Run by the maintainer.
- **D3. What an undo does, per pupil of the batch.** PROMOTED or REPEATED: the source enrolment goes back to ACTIVE (it was ACTIVE when the roll took it) and the new enrolment in the target session goes ACTIVE to CANCELLED. GRADUATED (source ALUMNI) or WITHDRAWN (source WITHDRAWN): the source enrolment goes back to ACTIVE; there is no new enrolment. A pupil the roll left alone ("skipped": they already had a place in the target session) was not touched and is not touched now.
- **D4. Whole roll or nothing, and it names the pupils that stop it.** The undo is refused (409 `UNDO_BLOCKED`, with a sentence and a list: pupil, admission number, reason) if, for any pupil, the placement has been used or changed since:
  - the source enrolment is not in the status the roll gave it (it was changed by hand since: re-enrolled, expelled, transferred...);
  - the new enrolment is not ACTIVE any more (the pupil was moved on, withdrawn, promoted again: a later roll);
  - the pupil has **activity in the target session**: a result or a report remark in a term of the target session, an invoice for a term of the target session, an attendance record dated within the target session. Marks, money and attendance are never silently orphaned or deleted by an undo.
  Nothing is changed in that case. The administrator fixes the cause (or accepts that the roll stands) and tries again. There is no partial undo: half an undone class is a worse state than either.
- **D5. Who.** The school's administrator only (`ADMIN`), with a **fresh proof** (the same re-authentication the school-level settings ask for: it is the most consequential edit of pupils' places in the product), and a **reason** of 1 to 500 characters. A campus administrator may roll a class of their own campus (task 0031) but may not undo it: ask the school's administrator. State-changing, so no support `area`.
- **D6. Atomic and concurrent-safe.** One transaction: the source and target enrolments of the batch are locked `FOR UPDATE` in id order (the order `executePromotion` uses, so two operations cannot wait on each other), every check is re-made under the lock, then the changes and the reversal row are written. Two undos at once: the second finds the reversal (the unique key) and is refused, nothing doubled. An undo and a roll of the same class at once serialise on the same locks.
- **D7. Rolling again after an undo.** The class can be rolled again: the preview and the roll treat a CANCELLED enrolment in the target session as "not placed" (the pupil is processed normally), and the roll **revives** that row (to ACTIVE, with the new arm) instead of creating a duplicate, which the unique key forbids. The new `PromotionRecord` points at the same enrolment row; that is allowed (a target enrolment is not unique across batches). A pupil enrolled by hand into the target session in the meantime has an ACTIVE enrolment there and is, as before, left alone. Enrolling a pupil by hand into a session where they have a CANCELLED enrolment revives it, as it already does for a WITHDRAWN one (`ENROLMENT_REACTIVATED`).
- **D8. Audited.** `PROMOTION_REVERSED` in the school's audit log: the batch, the reason, the counts (restored, cancelled), who. The reversal row holds the same. No pupil names in the audit (the batch's records have them).
- **D9. The screen.** In the History tab: an undone roll says "Undone on <date> by <name>: <reason>" and has no undo button; for a roll that can be undone, an administrator sees "Undo this roll" (a campus administrator does not). It opens a dialog that says what will happen in plain words, asks for the reason and the proof (the same step-up dialog the settings use), and, when the server refuses, lists the pupils and reasons it names. The page's sentence "A roll is never edited or removed." becomes "A roll is never edited or removed; one that was a mistake can be undone, and the undo is recorded too."
- **D10. What an undo does not do.** It does not reverse anything done to a pupil after the roll by other means (that is what D4 refuses); it does not restore marks; it does not touch the session's status; it does not undo "left alone" pupils.

## 5. Not in this task

- Undoing part of a roll (one pupil): use the people screens to move a pupil.
- Undoing a roll that has been used: the refusal names why; the school resolves it first.
- Editing a roll's decisions after it was made.
